# Execution ledger — RK3588 JPEG444 integrated pipeline probe

- Scope: 4 x 3840x540 libjpeg-turbo YUV444 encode, bounded queue, 4 persistent MPP MJPEG decoders, full 3840x2160 NV24 assembly.
- Acceptance: at least 1000 measured frames; paced output at least 60 fps; latency P99 below 50 ms; no sustained backlog, drops, decode errors, or checksum mismatch; output format NV24/4:4:4.
- Ruling: execute in the existing workspace because this is a board-coupled throwaway feasibility probe and its untracked input artifacts and ignored SSH credentials are already here; only `X-Workspace/jxs` probe/result files may be changed. Cost if wrong: this probe is not isolated from unrelated repository changes, so every final diff must be path-scoped.
- Ruling: the repeated natural frame is a capacity and latency workload, not evidence for arbitrary video content. Cost if wrong: a pass could be over-generalized beyond the tested content.
- Pre-flight: producer slots carry four JPEG buffers to one ordered consumer; consumer records completion only after all four MPP outputs are copied into the assembled NV24 frame. Static review complete; board reachable; MPP library and input present; governors initially `ondemand`.
- Smoke RED: MPP reported `Get no buffer from input packet` on all four decoders. Root cause: advanced task mode requires an MppBuffer-backed packet, while the probe wrapped ordinary heap memory with `mpp_packet_init`. Official `mpi_dec_multi_test.c` uses `mpp_packet_init_with_buffer` for this path.
- Smoke GREEN/function, RED/performance: MppBuffer-backed packets decode correctly to NV24 with a stable checksum, but measured about 316 ms decode+assemble and 3.17 fps. The official MJPEG advanced path marks each standalone JPEG packet EOS; the probe did not. Hypothesis: with `split_parse=1`, omitting EOS makes the parser wait for its packet-completion timeout despite the JPEG EOI marker. Minimal test: add EOS only, then rerun the identical smoke.
- EOS hypothesis disproved: identical smoke remained about 322 ms decode+assemble. Boundary timing showed MPP poll/decode at about 6-7 ms but each output copy at 76-79 ms. The probe wrapped the CPU read in `mpp_buffer_sync_ro_begin/end`; official MPP `dump_mpp_frame_to_file` reads a returned frame directly without that sync. Minimal test: remove only the redundant output sync and rerun with identical diagnostics.
- Output-sync hypothesis disproved: removing it left each tile copy at about 76-80 ms. Root cause is the output allocation type: plain DRM buffers are uncached for CPU reads. MPP exposes `MPP_BUFFER_FLAGS_CACHABLE`, and its own encoder test uses `MPP_BUFFER_TYPE_DRM | MPP_BUFFER_FLAGS_CACHABLE`. Minimal test: allocate the existing input/output group as cached DRM and restore read-side sync for correct device-to-CPU coherency.
- Cached DRM GREEN: tile copy fell to 3.7-5.6 ms and measured latency to 41.6-49.4 ms, with identical checksum and NV24 output. Decode+assemble remained 22.8-25.7 ms because four independent tile copies were serial on CPU0, limiting the two-frame smoke to 40.9 fps. Ruling: parallelize the four independent submit/wait/copy operations on CPU0-3, leaving CPU4-7 exclusively for encoding. Cost if wrong: MPP contexts could expose undocumented cross-context thread coupling; smoke and long-run error checks must catch it.
- Parallel wait/copy remained 23.2 ms and about 43.7 fps. Diagnostics show shared JPEG hardware completion staggered by about 3-4 ms per tile, while copy takes 4-7 ms and overlaps decode. Since decoded `h_stride` equals 3840, each Y and UV tile plane is contiguous; replace 1080 row copies with two plane copies to reduce CPU copy overhead without changing output.
- Contiguous CPU copy GREEN/latency but RED/throughput: 100 paced frames measured output 55.665 fps, latency P99 35.154 ms, decode+assemble P99 17.098 ms, and schedule lateness grew to 125.220 ms. This is a stable throughput failure. Ruling: test RK3588 RGA hardware assembly because it supports `RK_FORMAT_YCbCr_444_SP` and can place each decoded DMA buffer into a destination rectangle while preserving one contiguous NV24 output. Cost if wrong: the Orange Pi RGA driver or prebuilt userspace library may reject this format/operation; fall back to the measured CPU result if so.
- RGA RED: board driver/library version 1.10.6 rejected every tile with `Unsupported function: src unsupported YUV444 semi-planner 8bit format`; its runtime input-format list excludes YUV444SP even though current librga headers document the enum. Ruling: do not convert through another format because that would violate true 4:4:4 and add an unrequested transform; restore the verified CPU assembly path for final long runs. Cost if wrong: a different RGA driver/userspace stack could support NV24, but that is not the tested Orange Pi environment.
- Formal paced: 1000 measured frames, 58.301 fps, latency P99 35.939 ms, schedule lateness max 487.276 ms, 997 blocked frames, zero drops/errors/checksum mismatches, NV24 output; governors restored to `ondemand`.
- Formal saturated: 1000 measured frames, 55.452 fps, latency P99 36.586 ms, 997 blocked frames, zero drops/errors/checksum mismatches, NV24 output; governors restored to `ondemand`.
- Initial final candidate with per-frame checksum and DMC ondemand: FAIL — latency and 4:4:4 pass, but steady-state 60 fps and no-backlog criteria fail.
- Final-review ruling: the first formal runs checksum every 24.9 MB assembled frame before releasing the next slot. That correctly validates all 1000 outputs but adds non-codec work to service throughput. Preserve those runs as full-output correctness evidence, then rerun capacity with `JXS_CHECKSUM_EVERY=100` (first/last and every 100th frame sampled). Cost if wrong: sparse sampling could miss intermittent corruption, mitigated by the prior every-frame run of the same pipeline.
- Sampled-checksum paced with CPU performance but DMC ondemand: 58.572 fps, latency P99 36.698 ms, lateness max 404.297 ms; FAIL. Saturated under the same setup: 61.109 fps, proving core capacity exists but paced memory frequency behavior prevents delivery.
- Queue-capacity-4 paced test: 58.585 fps and latency P99 71.641 ms; FAIL. Ruling: bounded buffering cannot replace service capacity; keep queue capacity two.
- Root cause: DMC used `dmc_ondemand`, idled at 528 MHz, and rose to 2.112 GHz only under sustained load. Locking DMC to `performance` is required for predictable 60Hz operation.
- Final paced with CPU+DMC performance: 1000 frames, 60.001 fps, latency P99 32.561 ms/max 34.864 ms, lateness first/last/max 0.053/0.054/1.594 ms, seven transient blocked frames, zero drops/errors, 11 matching checksum samples, NV24.
- Final saturated with CPU+DMC performance: 1000 frames, 61.942 fps, latency P99 34.383 ms/max 36.494 ms, zero drops/errors, 11 matching checksum samples, NV24.
- Final: CONDITIONAL PASS for the repeated natural-frame, Q50, board-local scope when CPU and DMC are locked to performance; no claim for arbitrary content, network, or long-duration thermal behavior.
