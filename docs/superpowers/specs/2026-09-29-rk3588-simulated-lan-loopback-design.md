# RK3588 Simulated-LAN UDP Loopback Design

Date: 2026-09-29

## Objective

Extend the already passing RK3588 board-local JPEG 4:4:4 pipeline with a real
UDP/IP packetization and reassembly stage, then test whether the combined
encode, simulated-LAN transport, hardware decode, and NV24 assembly path can
sustain 4K60 with end-to-end P99 below 50 ms.

The test is deliberately a **simulated-LAN qualification**, not a physical-LAN
qualification. It must never be reported as evidence for a real NIC, cable,
switch, or second host.

## Selected simulation profile

- Endpoint: `127.0.0.1` on the Orange Pi 5 Plus.
- Transport: real Linux UDP/IP sockets.
- Datagram size: at most 1400 bytes including the custom transport header, so
  the traffic model stays below a 1500-byte Ethernet MTU after IP/UDP headers.
- Emulation: Linux `tc netem` on `lo`, one-way delay 1 ms, jitter 0.2 ms,
  normal distribution, and 1 Gbit/s rate.
- Loss: zero injected loss for the acceptance run.
- Codec: four 3840x540 JPEG 4:4:4 tiles at Q50, four Cortex-A76 software
  encoders, four persistent RK3588 MPP MJPEG decoders, contiguous NV24 output.
- Queue capacity: three frames, one bounded slot for each simultaneously active
  encode, UDP/network, and decode stage.
- Runtime: CPU policies and DMC governor locked to `performance` only during
  the run and restored afterward even on failure.

## Architecture and data flow

The existing board-local feasibility probe remains unchanged. A separate UDP
probe reuses its codec and NV24 assembly logic but inserts independent sender,
receiver/reassembly, and decoder threads:

`YUV444P8 -> four JPEG tiles -> UDP fragment sender -> lo/netem -> UDP receiver
-> per-frame tile reassembly -> four MPP decoders -> contiguous NV24`

Each UDP datagram has a versioned fixed-width header containing magic, frame
ID, tile ID, fragment index/count, tile byte length, byte offset, and payload
length. The receiver validates every field before copying, accepts reordered
fragments, rejects overlap/out-of-range metadata, detects duplicates, and only
releases a frame to the decoder after all four tiles are complete. Missing or
malformed data fails the run; it is not silently concealed.

The timestamp origin is immediately before four-tile encoding. Completion is
recorded only after all packets are reassembled, all four hardware decodes
finish, and the full NV24 frame is assembled. CSV output separates encode,
UDP transport/reassembly, decoder queue, decode/assembly, and total latency.

## Correctness and acceptance

Automated host-side protocol tests must first fail without the new protocol
implementation and then pass. They cover header round-trip, malformed metadata,
out-of-order fragments, duplicates, and complete reassembly.

Board acceptance uses at least 1000 measured frames after warm-up:

- paced output at least 60.000 fps with no accumulated schedule lateness;
- end-to-end P99 below 50 ms;
- zero dropped, malformed, duplicate-conflict, or decode-error frames;
- output remains MPP `NV24` / true 4:4:4;
- sampled assembled checksums remain stable for the repeated-frame workload;
- observed UDP byte and packet counts equal the derived counts;
- the active qdisc is captured in the evidence and removed afterward;
- CPU and DMC governors are verified restored after the run.

A saturated run measures available headroom but does not replace the paced
acceptance run. If the paced run fails, the result is reported as a simulated
LAN failure without weakening the criterion.

## Evidence and reporting boundary

Raw logs, CSV, qdisc state, system state, and an independent recomputation are
stored under `benchmark-results/rk3588-jpeg444-udp-loopback-20260929/`. The
summary and top-level feasibility report must state all of the following:

1. UDP/IP, packetization, reassembly, kernel queueing, and decode were real.
2. Propagation, jitter, and 1 Gbit/s serialization were generated by `netem`.
3. No physical Ethernet interface, cable, switch, or remote receiver was used.
4. The result is not physical-LAN qualification and cannot establish real-LAN
   loss, contention, NIC interrupt behavior, or clock synchronization.
